# Plan 4: Storage, Ingestion, Revision Review, and Publication Design

**Status:** Approved in design review

**Date:** 2026-08-09

**Depends on:** Plans 1-3 and `2026-08-08-bookstore-full-stack-design.md`

## 1. Purpose

Plan 4 replaces the browser-only publishing prototype with the first complete server-backed catalog workflow. An administrator can create a private title, upload an EPUB or CBZ/ZIP, wait for safe asynchronous ingestion, review the resulting reader content, configure a free preview, and deliberately publish or replace an edition. The original upload remains immutable and downloadable by an authorized administrator.

The implementation must preserve the central publication guarantee from the full-stack design: background work can prepare candidate revisions, but it can never expose them publicly or replace a live edition.

## 2. Goals

Plan 4 will provide:

- Provider-neutral private object storage with a working local adapter and an explicit S3 startup-failure stub.
- Streaming administrator uploads that do not buffer an entire book in the web process.
- Defensive EPUB and CBZ/ZIP ingestion in the existing worker.
- Immutable originals plus deterministic, regenerable reader assets.
- A database-backed prose and comic reader manifest.
- Private revision review, stable free-preview boundaries, and manual comic panel regions.
- Explicit first-publication, public-replacement, rollback, and withdrawal transactions.
- A real admin catalog workflow in place of the local-only Studio prototype.
- Public catalog details and free previews backed by the active database revision.
- The first admin-only audit dashboard.
- Local and Hetzner-oriented Docker Compose storage, maintenance, backup, and recovery documentation.

## 3. Non-goals

Plan 4 does not implement:

- S3 network operations. Selecting the S3 provider before its adapter is implemented must fail startup.
- Automatic panel detection or computer-vision analysis.
- Publisher-authored EPUB styling, scripting, fixed-layout rendering, DRM, audio, or video.
- PDF, DOCX, pasted-text, or loose-image ingestion.
- Checkout, Stripe reconciliation, entitlements, customer libraries, or customer original downloads.
- Sales analytics. Accurate copies sold, fees, refunds, and estimated payouts depend on the later commerce schema.
- Opening the production storefront. Production remains in maintenance mode until commerce and entitlement work is complete.
- Redis. The existing durable queue and outbox are PostgreSQL-backed, and this phase has no demonstrated Redis requirement.

## 4. Chosen architecture

The system uses three focused server modules:

1. **Storage** owns object keys and bytes. It exposes streamed writes, full and ranged reads, stat, server-side-style copy, delete, and bounded prefix listing. Callers never receive local filesystem paths.
2. **Ingestion** understands EPUB and CBZ/ZIP formats through the storage contract. It validates input lazily, produces deterministic derived objects, and builds a database manifest.
3. **Catalog** owns titles, revisions, covers, reader presentations, public visibility, and audit-producing state transitions.

This staged architecture is preferred over prebuilding a static reader bundle or parsing archives on every request. A database manifest supports stable semantic preview boundaries and editable panel regions, while derived objects make public reads predictable and keep archive parsing outside request paths.

The storage module may change implementation without changing catalog or ingestion behavior. The ingestion module may change its parser or derived formats without changing publication transactions. Catalog services do not parse files or manipulate local paths.

## 5. Storage contract

### 5.1 Operations

The storage interface accepts validated opaque object keys and provides:

- `write`: consume a stream while enforcing a byte limit and calculating metadata supplied by the caller.
- `read`: return a full stream.
- `readRange`: return a validated inclusive byte range for downloads and media responses.
- `stat`: return existence, byte size, modification time, and optional content metadata.
- `copy`: copy one object key to another without exposing a path to callers.
- `delete`: delete one exact object and treat absence as an idempotent success.
- `listPrefix`: return a bounded, paginated listing under one validated prefix for maintenance only.

There is no general recursive delete operation. Maintenance must enumerate candidates, prove each one is disposable, and delete exact keys.

### 5.2 Key policy

All keys are generated by application code from UUIDs and fixed path segments. User-supplied filenames are stored as metadata but are not used as path segments. Representative namespaces are:

- `staging/uploads/{uploadId}`
- `titles/{titleId}/revisions/{revisionId}/original`
- `titles/{titleId}/revisions/{revisionId}/derived/v1/...`
- `titles/{titleId}/covers/{coverId}`

The key validator rejects empty segments, dot segments, backslashes, absolute paths, control characters, encoded traversal, and keys outside the expected namespace. The local adapter resolves and verifies every target beneath one configured root before opening it.

### 5.3 Providers

`STORAGE_PROVIDER=local` uses a private directory. Development uses a repository-ignored bind mount; production uses a named Docker volume mounted into the web, worker, and explicit maintenance/tool containers only. Caddy never mounts the storage volume.

`STORAGE_PROVIDER=s3` constructs an unsupported-provider error during startup validation. The future adapter will implement the same interface and will not require catalog, route, or ingestion changes.

## 6. Upload and job flow

Only an actor with `catalog.manage` can upload a revision.

1. The upload endpoint accepts one multipart file, a title ID, a change summary, and an optional parent revision ID.
2. Before reading the body, it validates the title, expected title format, authorization, and request metadata.
3. It streams the file to a generated staging key while enforcing the compressed-size limit and calculating SHA-256. No route action reads the complete upload into memory.
4. After the stream closes successfully, one database transaction creates the `uploaded` revision, records its staging information, enqueues one deduplicated ingestion job through the existing queue/outbox infrastructure, and appends the upload audit event.
5. If the transaction fails, the staging object is an orphan eligible for delayed cleanup. If the stream fails, no revision or job is created.
6. The worker claims the job, moves the revision from `uploaded` to `processing`, validates and derives the content, and writes deterministic derived keys.
7. Only after all required objects exist does one transaction replace any prior manifest for that candidate, store the accepted original metadata, change the revision to `ready_for_review`, and append the completion audit event.
8. Post-commit cleanup deletes the staging key. Failure to delete it is harmless and recoverable by maintenance.

The accepted original is copied byte-for-byte to the revision's retained key. It is never modified in place. A retry may replace deterministic derived objects for the same revision but may not change the retained original's checksum.

## 7. Defensive archive validation

Uploads are untrusted input even though the route is administrator-only. Defaults are configurable, but production may not disable the structural safeguards.

Initial defaults are:

- 512 MiB maximum compressed upload.
- 2 GiB maximum declared and observed expanded content.
- 10,000 maximum archive entries.
- 100 megapixels maximum decoded dimensions per image.
- 8 MiB maximum individual XML/XHTML source document.
- Bounded filename length, normalized path depth, compression ratio, parser work, and wall-clock processing time.
- One concurrent ingestion job per worker process by default.

The archive reader operates lazily. Validation rejects:

- Absolute paths, drive-qualified paths, dot traversal, control characters, and path collisions after normalization.
- Symlinks and other non-regular entries.
- Encrypted entries and unsupported compression methods.
- Duplicate logical paths, inconsistent size declarations, entry-count excess, expanded-size excess, and dangerous compression ratios.
- Files whose signatures and decoded structures do not match their allowed content type.

File-signature detection is only an early hint. Acceptance always requires format-specific parsing or image decoding.

## 8. EPUB ingestion

Plan 4 supports reflowable EPUB 3 content that can be normalized into the Pale Orbit reader.

The ingester verifies the ZIP container, the required first and uncompressed `mimetype` entry, `META-INF/container.xml`, package document, manifest, reading order, navigation document, XHTML resources, and referenced images. It rejects DRM or encrypted resources, scripts, fixed-layout-only publications, remote resources, forms, embedded browsing contexts, and unsupported multimedia.

Publisher CSS and page layout are not preserved. Safe XHTML is converted into typed semantic blocks:

- Heading
- Paragraph
- Block quote
- Ordered or unordered list with list items
- Image with safe alternative text
- Thematic or section break

Inline fragments preserve safe emphasis, strong importance, code, subscript, superscript, and link text. External links are stored only after scheme validation and open outside the reader; links are never fetched during ingestion. Raw publisher HTML is not the reader's source of truth.

The package reading order defines section order. Navigation labels are used when valid, with deterministic safe fallbacks. Each section and block receives a stable database identifier, so the end of a preview is a semantic block boundary rather than a viewport page number or percentage.

Referenced JPEG, PNG, WebP, or GIF images are decoded, dimension-checked, orientation-normalized, and written as derived reader assets. Animated images use the first frame and add an ingestion warning. Required SVG resources and SVG spine documents are rejected rather than executing or incompletely sanitizing publisher-authored vector content. The embedded cover, when valid, becomes a revision-level cover suggestion only.

## 9. Comic ingestion

CBZ and ZIP comic uploads contain ordered raster page images. Accepted source types are JPEG, PNG, WebP, GIF, and TIFF. SVG pages are rejected. Animated images use the first frame and produce a visible admin warning.

Directory entries and recognized platform metadata such as `__MACOSX` and `.DS_Store` are ignored. Remaining pages use deterministic natural ordering across normalized relative paths and filenames. If two entries produce an ambiguous normalized order, ingestion fails rather than silently choosing a sequence.

Every page is decoded to verify its type and dimensions, orientation-normalized, and converted to a consistent web reader format. The manifest retains the source path as sanitized metadata, but public responses expose only page numbers and authorized asset URLs. The first valid page becomes a revision-level cover suggestion.

The base comic reader always supports whole-page reading. Guided panel mode is optional and manual. An administrator draws rectangles on a normalized coordinate space and controls their order. Guided mode can be published only when every page in the revision has at least one valid, non-degenerate ordered region and all coordinates remain within the page. No automatic panel detection is included.

## 10. Data model

### 10.1 Titles and covers

`titles` remains the mutable commercial/catalog record. It gains nullable confirmed-cover fields for storage key, content type, checksum, byte size, width, and height. Cover changes are independent from revisions: activation, replacement, and rollback never change the title cover automatically.

An admin may confirm an ingested cover suggestion or upload a separate JPEG or PNG. A separate cover upload is streamed, decoded, normalized, and stored before a transaction changes the title's cover pointer and appends an audit event. The previously referenced cover becomes eligible for delayed orphan cleanup only after the transaction commits.

### 10.2 Revisions

`title_revisions` remains the immutable-edition record and keeps the existing states:

`uploaded -> processing -> ready_for_review -> active -> retired`

Validation failure transitions `processing -> failed`. A retry transitions a retryable failed revision back through processing without creating a second revision. A revision stores the staging key while pending and the retained-original key, checksum, media type, byte size, and original filename only after acceptance. Safe failure code and details remain visible to administrators.

The parent revision expresses editorial lineage, not storage inheritance. Manifests are complete per revision.

`revision_cover_suggestions` stores at most one normalized suggestion per revision, including its storage key, source description, media type, checksum, byte size, and dimensions. Confirming a suggestion copies it into a new title-cover key and then changes the title pointer; it does not make the revision-owned derived object mutable.

`revision_ingestion_warnings` stores ordered, stable warning codes and safe messages for review. Warnings never contain raw markup, archive bytes, local paths, or unsanitized filenames.

### 10.3 Prose manifest

- `prose_sections`: revision ID, stable ID, reading-order ordinal, navigation label, and sanitized source reference.
- `prose_blocks`: revision ID, section ID, stable ID, block ordinal, block kind, and validated typed content data.
- `prose_images`: revision ID, stable ID, storage key, media type, checksum, byte size, dimensions, and safe alternative text.

Database uniqueness preserves section and block ordering within a revision. Same-revision composite foreign keys prevent blocks and images from crossing revision boundaries.

### 10.4 Comic manifest

- `comic_pages`: revision ID, stable ID, one-based page number, sanitized source path, storage key, media type, checksum, byte size, and dimensions.

Page number is unique within a revision. Same-revision foreign keys are used by presentation data.

### 10.5 Reader presentations

Reader settings are versioned separately from immutable content. `revision_presentations` belongs to one revision and has a state of `draft`, `published`, or `superseded`. Partial unique indexes permit at most one draft and one published presentation per revision.

A presentation contains reading direction and exactly one format-appropriate preview boundary:

- Prose: the final included section and block IDs.
- Comic: the final included one-based page number.

The catalog service validates that the referenced boundary belongs to the same revision and is reachable in reading order. It also requires a non-empty preview that ends before the end of the work; a free preview may not expose the complete revision.

`comic_panel_regions` belongs to a presentation and a same-revision comic page. It stores an ordinal plus normalized `x`, `y`, `width`, and `height` values. Database checks enforce positive size and the zero-to-one bounds; domain validation enforces completeness and deterministic order.

Publishing reader settings performs one transaction that supersedes the old published presentation, promotes the current draft, and clones the approved settings into a new draft baseline. Public requests therefore observe either the complete old settings or the complete new settings.

## 11. Revision and publication lifecycle

### 11.1 New private title

1. The admin creates a title with `private` visibility.
2. The admin uploads an original, creating an immutable candidate revision.
3. The worker moves the candidate to `ready_for_review` or `failed`.
4. The admin reviews the complete reader, original download, warnings, cover suggestion, preview boundary, and any comic panels.
5. The admin publishes the reader settings and activates the revision. The title remains private.
6. A distinct **Publish to storefront** action changes visibility to `public` after confirming that an active revision and published presentation exist.

If a private title already has an active revision, activation retires that revision, activates the reviewed candidate, changes `titles.active_revision_id`, and audits the change in one serialized transaction. Private activation never changes visibility.

### 11.2 Public replacement

Uploading or processing a candidate never changes the live edition. A public title does not offer a generic activation control. After review, **Publish replacement** performs one serialized database transaction that:

- Confirms the actor still has the required capability.
- Confirms the title is public and the candidate is `ready_for_review` with published reader settings.
- Retires the current active revision.
- Activates the candidate.
- Changes `titles.active_revision_id` to the candidate.
- Appends the audit event.

The old reader and original remain live until commit; the new reader and original become live together.

### 11.3 Rollback and withdrawal

Rollback selects a previously accepted retired revision with published settings. The same serialized transaction retires the current revision, activates the selected revision, changes the title pointer, and audits the action. Cover metadata does not roll back.

Withdrawal changes only `public -> private`. It removes the title and preview from public routes while preserving the active revision, files, revision history, and later entitlements. Re-publication requires an explicit action. Archiving is not a substitute for withdrawal and remains a separate later lifecycle concern.

No worker or maintenance task may change `titles.visibility`, `titles.active_revision_id`, or an active revision state.

## 12. Admin experience

`/admin/catalog` replaces the local-only publishing workflow. It lists titles with visibility, format, active revision, candidate status, settings-draft status, and safe ingestion failures.

The admin flow includes:

- Create and edit title metadata.
- Upload a revision and monitor asynchronous job status.
- Review extracted navigation or page order, warnings, failure details, and the full reader.
- Confirm an ingested cover suggestion or upload a separate cover.
- Set a semantic preview boundary.
- Draw, resize, delete, and reorder normalized comic panel regions.
- Publish reader settings.
- Activate a private revision.
- Publish a title for the first time.
- Publish a replacement for a public title.
- Roll back or withdraw with an impact summary and confirmation.
- Download a retained original through an authorized streaming endpoint.

Metadata and confirmed-cover edits use an explicit **Save** action. Once saved, they are immediately visible if the title is public. Preview boundaries and comic panels remain private drafts until **Publish reader settings** succeeds.

The current `/studio` route redirects to `/admin/catalog`. It does not retain an alternate local-storage publishing model or generate fake catalog entries.

## 13. Public catalog, reader, and file access

Public catalog and detail queries return only titles with `public` visibility, a valid active revision, and a published presentation. Knowing a private title ID, slug, revision ID, storage key, or derived-asset URL does not grant access.

Public reader endpoints resolve the active revision on every request and expose only the approved preview range. Prose responses end at the published semantic block. Comic responses end at the published page. Viewport pagination never influences authorization.

Every derived-asset and original-download request passes through server authorization before streaming. Responses use safe content types, content disposition, range handling, cache policy, and nosniff headers. They never return a local path or raw storage key.

During Plan 4:

- Administrators may read the full active or candidate revision and download accepted originals.
- Guests and signed-in non-admin users may read only a public title's free preview.
- Full customer reading and original downloads return a consistent unavailable/forbidden result until entitlement checks are implemented.

## 14. Audit dashboard

Plan 4 adds an admin-only audit dashboard backed by the append-only audit log from Plan 2. It provides cursor-based or stable keyset pagination, newest first, and filters for actor, action, resource type, resource ID, outcome, and date range.

The list view shows a safe summary. A detail view may show sanitized before/after context, correlation ID, request metadata, and failure classification. It never exposes password material, tokens, secrets, email contents, raw file bytes, or storage credentials.

Opening detailed audit context appends a separate `audit.event.view` event containing the viewed event ID. Ordinary list and filter operations are not audited, avoiding recursive noise.

Catalog actions introduced in this phase include audit events for upload acceptance, ingestion completion or failure, retry, metadata edit, cover change, settings publication, activation, storefront publication, public replacement, rollback, withdrawal, and original download.

## 15. Failure handling, idempotency, and cleanup

Ingestion failures affect only the candidate revision. They use stable non-sensitive codes and safe explanations. Unexpected error details remain in structured server logs, correlated by job and revision IDs, rather than in the database or browser.

Deterministic derived keys and manifest replacement make job retries idempotent. A retry must revalidate the retained or staged bytes and verify the expected checksum before changing database state. It may never mutate an active revision's content manifest. Regeneration of an accepted active revision, if needed later, requires a separate operational design.

Maintenance is an explicit tool command suitable for a scheduled host job. It supports dry-run mode and reports candidate counts and bytes. It may delete only:

- Staging uploads older than the configured retention period that are not needed by a live or retryable job.
- Derived objects whose revision does not exist or whose generation was never committed, after a safety delay.
- Superseded title-cover objects no longer referenced by any title, after a safety delay.

It may never delete a retained original. Deletes operate on exact validated keys. A database or storage error stops the current cleanup batch and leaves later candidates untouched.

## 16. Configuration and deployment

Development configuration remains in the ignored `.env` file. Production values are supplied by the host or deployment environment and Compose secrets; production does not depend on a checked-in `.env` file.

New configuration covers storage provider/root, upload and expansion limits, entry and image limits, processing timeout, staging retention, orphan safety delay, and worker ingestion concurrency. Configuration is parsed once at process startup with explicit bounds and environment-aware defaults.

The Docker image includes the native runtime required by the image processor. The production Compose stack mounts the same private storage volume into the app and worker. A maintenance profile mounts it only when the cleanup tool runs. Caddy has no storage mount.

The worker defaults to one ingestion job at a time on the Hetzner VPS. Existing CPU and memory limits remain authoritative and concurrency can increase only through explicit configuration. Readiness checks verify database access, worker heartbeat, and a non-content storage probe. Logs carry correlation, job, title, and revision IDs but not book contents or credentials.

Production remains in maintenance mode at the end of Plan 4.

## 17. Backup and recovery

PostgreSQL catalog data and the private storage volume are both durable source data and must be backed up. Redis is absent, and the PostgreSQL job queue can be rebuilt or allowed to resume after restore. Derived reader objects are regenerable in principle, but a normal backup includes them to reduce recovery time.

The runbook documents:

- A coordinated PostgreSQL and storage backup sequence.
- Capturing the application version and migration state with each backup.
- Verifying retained originals against stored SHA-256 checksums.
- Restoring into an isolated environment before replacing production state.
- Checking title/revision pointers, manifest counts, cover references, and sampled originals after restore.
- Disk-capacity monitoring and thresholds that block new uploads before the volume is exhausted.

The backup procedure must not rely on copying a live PostgreSQL data directory. It uses a supported logical or snapshot-consistent database backup mechanism.

## 18. Testing strategy

### 18.1 Unit tests

- Storage-key validation and local-root containment.
- Range parsing and safe download headers.
- Archive path normalization, collision detection, limits, natural ordering, and signature hints.
- EPUB package and navigation parsing, XHTML-to-block conversion, unsafe-content removal, and stable anchors.
- Comic page ordering, image constraints, preview pages, and normalized panel geometry.
- Revision state-machine and presentation-draft rules.

### 18.2 Integration tests

Integration tests use real PostgreSQL, the existing queue/worker infrastructure, and an isolated temporary local-storage root. They cover representative minimal EPUB and CBZ fixtures, rejected archives, successful ingestion, retry after interruption, transactional manifest replacement, cleanup safety, activation, settings publication, first publication, public replacement, rollback, withdrawal, and audit events.

Tests prove that a failed or in-progress candidate cannot affect a public title and that public readers never observe a mixed revision or draft presentation.

### 18.3 Route and browser tests

Route tests cover admin authorization, CSRF/origin protections inherited from the app, upload limits, private-object denial, preview truncation, full-reader denial, original-download authorization, range responses, and safe failures.

Browser tests cover the primary admin journey from title creation through upload, review, preview configuration, private activation, and publication. Separate journeys cover comic panel editing, public replacement, rollback, withdrawal, and audit filtering/detail access.

### 18.4 Verification gates

The phase is complete only when type checking, lint, unit tests, PostgreSQL integration tests, browser tests, web and service builds, migration checks, runtime dependency audit, and development/production Compose validation pass. Native image-processing support must be exercised in both the development host environment and the production image.

## 19. Dependency policy and standards

Implementation will select maintained Node 26-compatible packages immediately before installation and record exact lockfile results. Likely responsibilities are:

- A lazy ZIP reader with entry-size validation and stream-based extraction.
- A maintained XML parser configured to avoid unsafe entity behavior.
- A native image decoder/processor with explicit pixel and animation limits.
- A file-signature helper used only as an early hint, never as the acceptance decision.

The implementation plan must verify current releases and compatibility from the official registry and project documentation rather than locking versions in this design.

Normative and primary references:

- [EPUB 3.3 specification](https://www.w3.org/TR/epub-33/)
- [yauzl documentation](https://github.com/thejoshwolfe/yauzl)
- [sharp documentation](https://sharp.pixelplumbing.com/)
- [file-type documentation](https://github.com/sindresorhus/file-type)
- [fast-xml-parser documentation](https://github.com/NaturalIntelligence/fast-xml-parser)

## 20. Acceptance criteria

Plan 4 is accepted when:

1. An administrator can upload a valid EPUB or CBZ/ZIP without buffering the whole file in the web process.
2. Unsafe or unsupported archives fail with a stable safe explanation and cannot change a live title.
3. A successful revision has an immutable retained original, complete database manifest, deterministic reader assets, and private full preview.
4. EPUB previews stop at a published semantic block and comic previews stop at a published page.
5. Comic guided mode appears only for complete, valid, published manual panel data.
6. Title covers change only through an explicit title-level action.
7. Draft reader settings do not affect public readers until explicitly published.
8. First publication, public replacement, rollback, and withdrawal are explicit audited transactions with no mixed-edition window.
9. Public users cannot access private titles, candidate revisions, full works, retained originals, or storage paths.
10. Admins can browse filtered audit events and audited event details without exposing sensitive data.
11. Cleanup can remove proven staging/orphan data in dry-run and active modes and cannot delete retained originals.
12. The local development and production Compose configurations validate with private storage mounts and production maintenance mode.
13. The full automated verification suite and production builds pass.
